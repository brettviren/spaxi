#+title: spaxi — a pixi-like experience for Spack packages

~spaxi~ explores two strategies for giving Spack-built software the
smooth end-user experience that [[https://pixi.sh][pixi]] provides for conda packages.

* Strategy 1: convert Spack installs to conda packages

** Provider workflow:

This results in conda package format version 2 which make use of "flags".

1. Use =spack= to install a "spec" (package and its dependency tree).
2. Use =spaxi conda= to convert the installed spec to conda packages in a local "channel" directory.
3. Optional, publish/sync channel directory to an online instance.

See [[file:examples/provider-conda.sh]] for example.

** User workflow:

1. Given the channel, use =pixi= as normal to initialize a project.
2. Edit =pixi.toml= to set glibc version to what is in the channel (see below).
3. Use =pixi add <pkg>= to add packages as normal (beware ambiguity)
3. Optional, use =spaxi add-spec <spec>= which can add packages unambiguously.

See [[file:examples/enduser-pixi.sh]] for example.

*** Details - libc

By default, packages from Spack are built with a Spack-built =libc= while =pixi=
wants to use the system =libc= by default.  When the two have different versions
you must encode the Spack-built version for =pixi=:

#+begin_src toml
[workspace]
platforms = [{ platform = "linux-64" , glibc = "2.36" }]
# ...
#+end_src

*** Details - ambiguities 

In addition to a name and a version, a concrete Spack "spec" (an installed
package) has a set of "variants" which are either binary true/false or
name/label parameters.  Spaxi maps Spack variants to Conda "flags".  Flags may
be new to many pixi users.  A =pixi.toml= may specify matches on flags and their
values similarly to how matches on the "build" string have been traditionally
made.

A Spack packages may have multiple installed instances for the same name and
version and this translates to the channel that spaxi populates.  If the
end-user of =pixi= does not specify sufficient number of flags to match it is
possible their pixi environment selects among the ambiguous package set in a
"random" way.

Unlike Spack, Conda packages and =pixi.toml= have no way to specify unambiguously
specify a dependency between multiple packages that have the same name, version
and variant set but differ in terms of their sets of dependencies.  Spaxi
provides a way to encode a specific "spec" by giving a flag named =hash= that
matches against the Spack hash.  The =spaxi add-spec --exact <spec>= will update
=pixi.toml= to include the hash corresponding to the =<spec>= (if the spec is
unique).


* Strategy 2: pixi-like workflow, purely Spack

~spaxi~ offers pixi-equivalent subcommands that stay entirely within
Spack — no conda involved.  A project directory holds a ~spaxi.toml~
manifest (analogous to ~pixi.toml~); a Spack environment under
~.spaxi/env/~ realizes it and maintains a merged view (bin/, lib/, …)
at ~.spaxi/envs/default/~.  Spack does the solving and installing, so
Spack binary build caches are used whenever the Spack configuration
provides them.

#+begin_example
$ spaxi init            # create spaxi.toml in the current directory
$ spaxi add zstd@1.5:   # add a spack spec and install it
$ spaxi list            # installed packages in the environment
$ spaxi tree            # dependency tree
$ spaxi info            # project paths and dependencies
$ spaxi remove zstd     # drop a dependency
$ spaxi install         # (re)install everything in spaxi.toml
#+end_example

The manifest keys dependencies by package name with the rest of the
spack spec as the constraint:

#+begin_example
[project]
name = "demo"

[dependencies]
zstd = "@1.5:"
#+end_example

* Configuration

Following the XDG convention, ~spaxi~ reads
~~/.config/spaxi/config.toml~ (or the file given with ~-c/--config~).
Values are layered last-one-wins: environment variables → config file
→ command line options.

| section.key     | environment variable  | command line  | meaning                       |
|-----------------+-----------------------+---------------+-------------------------------|
| ~spack.exe~     | ~SPAXI_SPACK_EXE~     | ~--spack-exe~ | path to the spack executable  |
| ~conda.channel~ | ~SPAXI_CONDA_CHANNEL~ | ~--channel~   | local conda channel directory |

If no spack executable is configured, ~spaxi~ tries ~./spack/bin/spack~
then ~spack~ on ~$PATH~.
