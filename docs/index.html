spaxi

A pixi-like end-user experience for Spack-built software — either by converting Spack installs into genuine conda packages, or by wrapping Spack itself in a pixi-shaped workflow.

Two strategies

Both strategies involve two roles: a provider who builds software with Spack and publishes it, and an end-user who installs it into per-project environments. They differ in what crosses the wire.

Strategy 1 · conda channel

Spack builds → conda packages → pixi

The provider converts Spack install trees into .conda packages (spaxi conda) and serves them as a static conda channel. End-users need only pixi — no Spack at all.

spack install→ spaxi conda→ channel/→ pixi add
Strategy 2 · pure Spack

Spack build cache → spaxi project

Everything stays in Spack. The provider publishes a binary build cache; end-users drive per-project Spack environments through pixi-equivalent spaxi subcommands.

spack install→ buildcache push→ mirror→ spaxi add

All scripts referenced below live in docs/examples/ and are runnable as-is. Each one first sources spack-env.sh, which isolates Spack's configuration and caches under a local .cache/ directory:

SPAXI_CACHE="${SPAXI_CACHE:-$PWD/.cache}"

export SPACK_USER_CONFIG_PATH="$SPAXI_CACHE/spack/user-config"
export SPACK_USER_CACHE_PATH="$SPAXI_CACHE/spack/user-cache"
export SPACK_SYSTEM_CONFIG_PATH="$SPAXI_CACHE/spack/system-config"

Strategy 1 — publish a conda channel, install with pixi

spaxi conda <spec> resolves the spec against the installed Spack packages (it must match exactly one — qualify with /<hash> if ambiguous) and converts the install tree into a package in the current conda format: a .conda archive (conda_pkg_format_version 2), placed into a channel directory with maintained repodata.json indices. Transitive runtime dependencies are converted along with it, so the channel is self-contained.

  • The conda build string is the Spack DAG hash; runtime dependencies become exact name version build pins, so a channel can carry many builds of one version side by side.
  • glibc maps to conda's __glibc virtual package; other external (non-Spack-built) dependencies are skipped.
  • Files embedding the Spack prefix are recorded in info/paths.json with a prefix_placeholder (text or binary mode). The installer — pixi, conda, mamba — rewrites them to the target environment prefix at install time, exactly as it does for conda-build packages. RPATHs therefore point into the end-user environment after installation.
  • The original spec.json rides along as info/spack-spec.json for provenance.
Prefix length is the one hard constraint. Binary relocation rewrites the placeholder in place, so the end-user environment prefix must be no longer than the provider's Spack install prefix. Providers should set spack config add config:install_tree:padded_length:128 (or more) before building, which pads install prefixes the same way Spack does for its own public build caches. spaxi conda prints the resulting limit for each package it builds.

Provider provider

Script: provider-conda.sh — provider-conda.sh [spec] [channel-dir]

  1. Isolate Spack configuration (source spack-env.sh).
  2. Pad install prefixes: spack config add config:install_tree:padded_length:128.
  3. Build the software with the executables you want: spack install "zstd +programs". Spack's zstd defaults to ~programs (library only), so the zstd CLI would be absent from the channel unless you request +programs.
  4. Convert and index: spaxi --channel ./channel conda "zstd +programs".
  5. Publish channel/ via any static file server (or share the path).
  6. Note the build machine's glibc (spack find --format '{version}' glibc); it becomes the packages' __glibc >= floor. End-users usually need not act on it — see below.
# the heart of provider-conda.sh
. spack-env.sh
"$SPACK" config add config:install_tree:padded_length:128
"$SPACK" install "$SPEC"        # SPEC defaults to: zstd +programs
spaxi --spack-exe "$SPACK" --channel "$CHANNEL" conda "$SPEC"

End-user end-user

Script: enduser-pixi.sh — enduser-pixi.sh <channel-url> [package] [glibc-version]

The end-user machine needs pixi only. Two things to know:

  1. Spack-built packages carry a __glibc >= constraint from the provider's build machine. pixi models glibc as the __glibc virtual package and auto-detects it from this host (see pixi info → "Virtual packages"), so on a machine whose glibc already satisfies that constraint nothing extra is required — the platforms = [{ platform = "linux-64" }] that pixi init writes is enough. Pin it (glibc = "2.36") only when solving for a different machine than the one running pixi. The old top-level [system-requirements] table is deprecated.
  2. Keep the project path reasonably short (see the prefix-length note above).
# the heart of enduser-pixi.sh
pixi init --channel "$CHANNEL" .

# glibc is auto-detected from the host, so no [system-requirements] and
# no glibc pin are needed here.  Pin only for a cross-machine solve:
#   platforms = [{ platform = "linux-64", glibc = "2.36" }]

pixi add zstd

# the Spack-built program runs straight from the pixi env
pixi run which zstd        # -> .pixi/envs/default/bin/zstd
pixi run zstd --version    # -> *** zstd command line interface 64-bits v1.5.7 ...

After pixi add, the environment at .pixi/envs/default contains the Spack-built libraries and executables with all prefixes — including RPATHs — rewritten to point into the pixi environment.

Strategy 2 — pixi-shaped workflow, purely Spack

No conda anywhere: a spaxi project is a directory with a spaxi.toml manifest (the analogue of pixi.toml). A Spack environment under .spaxi/env/ realizes the manifest and maintains a merged view — bin/, lib/, include/ — at .spaxi/envs/default/. Spack does all solving and installing, so binaries come from any configured Spack build cache and are relocated by Spack itself; there is no prefix-length concern in this strategy.

[project]
name = "demo"

[dependencies]
zstd = "@1.5:"        # key = package, value = rest of the spack spec

Provider provider

Script: provider-spack.sh — provider-spack.sh [spec] [mirror-dir]

The provider's job is to publish a Spack binary build cache so end-users never compile:

# the heart of provider-spack.sh
. spack-env.sh
"$SPACK" install "$SPEC"
"$SPACK" buildcache push --unsigned "$MIRROR" "$SPEC"
"$SPACK" buildcache update-index "$MIRROR"

Publish the mirror directory via any static file server. For production use, sign the packages (drop --unsigned) and distribute the public key.

End-user end-user

Script: enduser-spaxi.sh — enduser-spaxi.sh [package] [mirror-url]

The end-user needs Spack and spaxi. Register the provider's build cache once, then work entirely in pixi-style commands:

# the heart of enduser-spaxi.sh
. spack-env.sh
"$SPACK" mirror add --unsigned provider "$MIRROR"

spaxi init --name demo
spaxi add zstd            # solve + install (from the build cache) + view
spaxi list
spaxi tree
export PATH="$PWD/.spaxi/envs/default/bin:$PATH"

Configuration

spaxi follows the freedesktop XDG convention: it reads ~/.config/spaxi/config.toml or the file given with -c/--config. Values are layered last-one-wins: environment variables → config file → command line options.

config keyenvironment variablecommand linemeaning
spack.exeSPAXI_SPACK_EXE --spack-exePath to the spack executable (default: ./spack/bin/spack, then spack on $PATH).
conda.channelSPAXI_CONDA_CHANNEL --channelLocal conda channel directory for spaxi conda (default: ./channel).

When exercising Spack itself, keep its state local and reproducible by setting the three SPACK_*_PATH variables shown at the top — every example script does this automatically.
